A2A, MCP, AI Agent 각각의 구분이 모호하다.

AI라는 단어의 특성인가 싶을 정도로 AI가 들어가는 모든 도메인에는 모호함이 함께한다.

이 흐릿한 개념들을 **개발자 관점**에서 조금 더 선명하게 보정해보자.

## 1. 핵심 정의: 직원, USB, 그리고 회의

세 가지 용어의 관계를 가장 직관적인 **'회사 업무'** 에 비유하여 정의할 수 있다.

<Callout type="info" title="3줄 요약 비유">
  * <Strong>AI Agent (직원):</Strong> 일을 스스로 처리하는 주체.
  * <Strong>MCP (USB 포트):</Strong> 직원이 도구(DB, API)를 쓰기 위한 연결 표준.
  * <Strong>A2A (협업 회의):</Strong> 직원들끼리 소통하며 복잡한 문제를 해결하는 방식.
</Callout>

### ① AI Agent (에이전트)
* <Strong>정의:</Strong> 환경을 인식하고, 추론하며, 목표를 달성하기 위해 자율적으로 도구를 사용하여 행동하는 소프트웨어 주체다.
* <Strong>핵심:</Strong> 내가 기존에 이해하던 특정 동작, **도메인에 특화된 AI 모듈에 '자율성'과 '계획 수립(Planning)' 능력이 포함된 것**을 에이전트라 칭한다.
* <Strong>역할:</Strong> 작업을 수행하는 **실무 직원**.

### ② MCP (Model Context Protocol)
* <Strong>정의:</Strong> Anthropic에서 제안한 오픈 표준으로, AI 모델이 데이터(DB), 기능(Tools), 리소스에 접근하는 방식을 표준화한 인터페이스다.
* <Strong>핵심:</Strong> 과거에는 AI를 DB에 연결하기 위해 전용 파이프라인을 짰어야 했지만, MCP를 쓰면 **마치 USB를 꽂듯** 표준화된 방식으로 AI와 데이터를 연결할 수 있다.
* <Strong>역할:</Strong> Agent가 외부 시스템을 활용하기 위한 **연결 포트**.

### ③ A2A (Agent-To-Agent)
* <Strong>정의:</Strong> 하나의 거대 모델(God Model)이 모든 걸 처리하는 것이 아니라, 여러 개의 전문화된 AI Agent가 서로 소통하고 협력하여 복잡한 문제를 해결하는 **상호작용 패턴**이다.
* <Strong>핵심:</Strong> 오케스트레이션(Orchestration)이나 스웜(Swarm) 구조에서 나타난다. 상위 에이전트가 하위 에이전트에게 작업을 위임하거나 결과를 취합한다.
* <Strong>역할:</Strong> 직원들 간의 **협업 회의** 또는 **업무 지시 체계**.

## 2. 한 눈에 비교하기

세 개념은 기술적 레이어(Layer) 자체가 다르다.

| 구분 | AI Agent | MCP (Model Context Protocol) | A2A (Agent-to-Agent) |
| :--- | :--- | :--- | :--- |
| **비유** | <Strong>작업자 (Worker)</Strong> | <Strong>USB-C 포트 (Interface)</Strong> | <Strong>팀워크 (Collaboration)</Strong> |
| **주된 목적** | 과업(Task)의 자율적 수행 | AI와 외부 시스템(DB, API) 연결 | 복잡한 문제의 분업 및 해결 |
| **구성 요소** | LLM + 메모리 + 계획 + 도구 | Client, Host, Server | Orchestrator, Workers |
| **핵심 동작** | 생각(Think) $\rightarrow$ 행동(Act) | 요청(Request) $\leftrightarrow$ 응답(Response) | 위임(Delegate) $\leftrightarrow$ 보고(Report) |
| **위치** | Application Logic Layer | Interface / Protocol Layer | Architecture Layer |

## 3. AI Agent 서비스 개발의 3단계

이제 이 개념들이 실제 개발 프로세스에 어떻게 녹아드는지 살펴보자. 개발 순서는 보통 **Bottom-Up** 으로 진행된다.

<Steps>
  <Step title="1단계: MCP 툴 개발 (Backend / Integration)">
    * **하는 일:** 레거시 시스템, 사내 DB, 슬랙, 깃허브 등을 AI가 이해할 수 있는 **MCP Server** 표준으로 래핑한다.
    * **비유:** 직원들이 사용할 '도구'와 '매뉴얼'을 만드는 과정.
    * **결과물:** `weather-mcp-server`, `database-mcp-server`
  </Step>
  
  <Step title="2단계: Agent 정의 및 MCP 할당 (Persona Configuration)">
    * **하는 일:** 특정 LLM 모델에 **System Prompt(페르소나)**를 부여하고, 1단계에서 만든 MCP Tool 목록 중 그에게 필요한 것만 쥐어준다.
    * **비유:** "너는 이제부터 '여행 상담사'야. 이 '항공권 검색 도구(MCP)'를 써서 일해."라고 임명하는 과정.
  </Step>
  
  <Step title="3단계: A2A 오케스트레이션 (Application Logic)">
    * **하는 일:** 여러 Agent들이 어떤 순서로 일할지, 누가 누구에게 보고할지, 에러가 나면 누가 해결할지 워크플로우를 코드로 짠다.
    * **비유:** 팀장(Orchestrator)이 직원들의 업무 순서를 정하고 관리하는 과정.
  </Step>
</Steps>
