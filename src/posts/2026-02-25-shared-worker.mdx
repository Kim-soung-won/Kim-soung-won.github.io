현대의 웹 애플리케이션은 라이브 대시보드, 공동 편집 도구, 멀티플레이어 게임 등 끊임없는 실시간 상호작용(Real-time Communication)을 요구합니다. 이를 위해 프론트엔드 생태계는 **WebSocket**과 **SSE(Server-Sent Events)**를 적극적으로 채택해 왔습니다.

하지만 이 기술들은 사용자의 **'다중 탭(Multi-tab)'** 브라우징 패턴과 결합하면서 예상치 못한 거대한 아키텍처적 병목 현상을 야기했습니다.

## 1. 다중 탭 환경의 충돌과 서버 인프라의 위기

전통적인 프론트엔드 아키텍처에서는 각각의 브라우저 탭이 완전히 독립적인 실행 컨텍스트를 가집니다. 즉, 한 사용자가 15개의 탭을 열어둔다면 **15개의 독립적인 웹소켓/SSE 커넥션**이 서버와 맺어집니다.



<Callout type="danger" title="분산 서버 인프라의 병목">
  클라이언트의 중복 커넥션은 로드 밸런서의 세션 추적 부하를 가중시키고, 백엔드 노드 간 상태 동기화를 위한 내부 메시지 브로커(Redis, RabbitMQ 등)의 글로벌 통신량을 폭증시킵니다. 
  
  또한, 브라우저의 동일 도메인 동시 커넥션 제한(보통 6개)에 걸려, 일반적인 API 요청조차 무한 대기(Pending) 상태에 빠지는 현상이 발생합니다.
</Callout>

이를 극복하기 위해 클라이언트 단에서 커넥션을 하나로 묶어 서버로 전달하는 **'커넥션 일원화(Connection Centralization)'** 전략이 대두되었습니다.

## 2. 웹 통신 프로토콜 비교: WebSocket vs SSE

커넥션 일원화를 논하기 전, 기반이 되는 두 프로토콜의 특성을 명확히 해야 합니다.

| 특성 / 지표 | WebSocket | Server-Sent Events (SSE) |
| :--- | :--- | :--- |
| **통신 방향성** | 전이중 (Full-duplex), 양방향 | 단방향 (Server to Client) |
| **기반 프로토콜** | 초기 핸드셰이크 후 독자적 프로토콜로 격상 | 순수 HTTP/1.1, HTTP/2 활용 |
| **데이터 포맷** | 바이너리 및 텍스트 프레임 | 텍스트 기반 스트림 (UTF-8) |
| **연결 복구** | 직접 구현 필요 | 네이티브 자동 재연결 및 Last-Event-ID 지원 |
| **이상적 유스케이스** | 멀티플레이어 게임, 양방향 협업 툴 | 라이브 대시보드, 주식 시세, 단방향 피드 |

## 3. Web Worker 생태계와 Shared Worker의 위상

이러한 네트워크 커넥션을 메인 스레드(UI)와 격리하여 중앙 통제하기 위해 Web Worker API를 활용합니다. 

<Tabs items={['Dedicated Worker', 'Service Worker', 'Shared Worker (Core)']}>
  <Tab>
    **전용 워커 (Dedicated Worker)**
    * **접근성:** 자신을 생성한 단일 탭에서만 독점 접근.
    * **생명주기:** 부모 탭이 닫히면 즉시 강제 종료.
    * **용도:** 무거운 CPU 연산 (이미지 처리, 파싱). 커넥션 공유 불가.
  </Tab>
  <Tab>
    **서비스 워커 (Service Worker)**
    * **접근성:** 스코프 내의 통제 가능한 모든 페이지.
    * **생명주기:** 이벤트 기반 동작 후 휴면/종료 (불연속적).
    * **용도:** 오프라인 캐싱, PWA, 푸시 알림. 장시간 커넥션 유지에는 부적합.
  </Tab>
  <Tab>
    **공유 워커 (Shared Worker)**
    * **접근성:** 동일 오리진을 공유하는 모든 탭, 윈도우, iframe에서 접근 가능.
    * **생명주기:** 참조하는 페이지가 하나라도 존재하면 영구 동작.
    * **용도:** **웹소켓/SSE 커넥션 일원화**, 다중 탭 상태 동기화의 단일 진실 공급원(SSOT).
  </Tab>
</Tabs>

## 4. 멀티플렉싱과 양방향 라우팅 설계 패턴

Shared Worker를 라우터로 활용하는 아키텍처는 정교한 비동기 통신 설계를 요구합니다.



### 상관관계 식별자(Correlation Identifier)를 이용한 라우팅
단일 웹소켓에 수많은 탭이 몰려있을 때, 서버에서 온 응답이 **어느 탭의 요청에 대한 결과인지** 식별하기 위해 다음 패턴을 사용합니다.

<Steps>
  <Step title="1. 식별자 발급">
    특정 탭에서 요청이 발생하면 고유한 난수(`callbackId`)를 생성하고, 이를 키(Key)로 콜백 함수를 탭 내부 딕셔너리에 등록합니다.
  </Step>
  <Step title="2. 캡슐화 및 발송">
    생성된 ID와 페이로드가 Shared Worker로 전달되고, 워커는 단일 웹소켓을 통해 서버로 전송합니다.
  </Step>
  <Step title="3. 서버 회신">
    서버는 로직 처리 후, 클라이언트가 보낸 `callbackId`를 그대로 포함시켜 결과 페이로드를 워커로 보냅니다.
  </Step>
  <Step title="4. 다운스트림 분배">
    워커는 연결된 모든 탭(MessagePort)에 메시지를 브로드캐스트합니다. 각 탭은 `callbackId`를 대조하여 자신의 딕셔너리에 일치하는 식별자가 있을 때만 UI를 업데이트합니다.
  </Step>
</Steps>

## 5. 메모리 누수 방어: 가비지 컬렉션 최적화

Shared Worker 아키텍처의 가장 치명적인 약점은 탭이 닫힐 때 `MessagePort` 객체가 해제되지 않아 발생하는 **메모리 누수(Memory Leak)**입니다. 죽은 포트에 브로드캐스트를 시도하면 CPU 스파이크가 발생합니다.



<Tabs items={['명시적 해제 (전통적)', 'WeakRef (지연 평가)', 'FinalizationRegistry (최적화)']}>
  <Tab>
    `beforeunload` 이벤트를 캡처하여 워커에 포트 삭제를 지시합니다. 하지만 브라우저 크래시나 OS 강제 종료 시 이벤트 호출이 보장되지 않는 한계가 있습니다.
  </Tab>
  <Tab>
    모던 JS 스펙인 `WeakRef`로 포트를 래핑하여 보관합니다. 브로드캐스팅 시 `deref()`를 호출하여 `undefined`가 반환되면 가비지 컬렉팅된 것으로 간주하고 배열에서 삭제합니다.
  </Tab>
  <Tab>
    포트가 가비지 컬렉팅되는 순간을 옵저빙하여 비동기 콜백을 실행하도록 스케줄링합니다. 콜백 내부에서 포트를 상수 시간으로 삭제하여 브라우저 엔진과 완벽히 동기화된 메모리 관리를 이뤄냅니다.
  </Tab>
</Tabs>

## 6. 모바일 파편화 극복: 리더 선출(Leader Election) 폴백

아키텍처적 완성도에도 불구하고, **Android Chrome 브라우저는 현재까지도 Shared Worker를 지원하지 않습니다.** 이를 극복하기 위해 분산 컴퓨팅 이론을 차용한 **리더 선출(Leader Election) 아키텍처**를 사용합니다.



<Steps>
  <Step title="1. 원자적 권한 획득 (Web Locks API)">
    모든 탭은 `navigator.locks.request()`를 호출하여 독점적 락(Lock)을 요청합니다. 브라우저 스케줄러에 의해 단 하나의 탭만이 **'리더(Leader)'**로 승격되어 웹소켓 커넥션을 수립합니다.
  </Step>
  <Step title="2. 브라우저 내부 IPC 구축 (Broadcast Channel API)">
    권한을 얻지 못한 나머지 탭(팔로워)들은 직접 서버와 통신하지 않고, `Broadcast Channel`을 통해 리더 탭에게 모든 요청을 위임합니다.
  </Step>
  <Step title="3. 결함 허용(Fault Tolerance)과 Failover">
    리더 탭이 강제 종료되거나 크래시되면 브라우저는 즉시 락을 회수합니다. 대기 중이던 다음 팔로워 탭의 프로미스가 즉각 실행되며 **새로운 리더로 승격**, 수십 밀리초 내에 커넥션을 재건합니다.
  </Step>
</Steps>
