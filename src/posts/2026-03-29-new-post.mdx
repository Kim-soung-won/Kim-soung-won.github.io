툴팁은 UI에서 가장 흔하게 쓰이는 컴포넌트 중 하나지만, 의외로 "망가지기 쉬운" 컴포넌트이기도 합니다.

단순한 정적 페이지에서는 `position: absolute`와 CSS `::before`만으로도 잘 동작합니다. 하지만 실제 앱에서는 카드 안에, 모달 안에, 애니메이션 컨테이너 안에 들어가면서 조용히 잘리거나, 다른 요소 뒤로 숨거나, 예상치 못한 위치에 나타나는 문제가 생깁니다.

이 글은 **툴팁이 가려지는 세 가지 근본 원인**을 분석하고, 어떤 부모 구조를 갖든 항상 같은 형태로 렌더되는 툴팁을 설계하는 방법을 다룹니다.

---

## 1. 툴팁이 보이지 않는 세 가지 원인

### 원인 1 — `overflow: hidden`

`position: absolute`인 요소는 **가장 가까운 positioned 조상**(position이 static이 아닌)을 기준으로 배치됩니다.
그런데 그 조상이 `overflow: hidden`을 갖고 있으면, 요소 박스를 벗어나는 모든 자식은 잘립니다.

```
┌───────────────────────────────┐  ← overflow: hidden
│                               │
│  [버튼]                        │
│    ┌──────────────────┐       │   ← 이 영역 밖은 잘림
│    │  툴팁            │       │
│    └──────────────────┘       │
│ ✂ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │
└───────────────────────────────┘
```

카드 컴포넌트, 모달, 스크롤 영역 등이 주로 `overflow: hidden`을 사용하기 때문에, 실제 앱에서 가장 자주 마주치는 원인입니다.

<Callout type="info" title="overflow: hidden이 필요한 이유">
`border-radius`가 적용된 요소 내부의 자식이 모서리를 넘어가는 것을 막기 위해 `overflow: hidden`을 함께 쓰는 패턴이 흔합니다.
그래서 카드 컴포넌트는 `overflow: hidden`을 갖는 경우가 많고, 그 안의 툴팁이 조용히 잘립니다.
</Callout>

### 원인 2 — `transform`이 만드는 containing block 함정

많은 개발자가 `position: fixed`면 `overflow: hidden`을 탈출할 수 있다는 사실을 알고 있습니다. 맞습니다. 하지만 함정이 하나 더 있습니다.

CSS 명세에 따르면, **`transform`, `filter`, `will-change`, `perspective` 속성이 있는 요소는 새로운 containing block을 형성**합니다. `position: fixed`인 자식 요소는 viewport가 아닌 이 요소를 기준으로 배치됩니다.

<Quote>
`transform: translateX(0)`처럼 아무런 시각적 변화가 없는 선언도 containing block을 만들어냅니다.
</Quote>

```css
/* 이것만으로도 하위 fixed 요소의 기준점이 됩니다 */
.animation-container {
  transform: translateX(0);
}
```

다크모드 전환 애니메이션, 슬라이드 인/아웃, 카드 hover 효과 등에서 `transform`을 쓰는 경우 이 문제가 발생합니다.

### 원인 3 — z-index Stacking Context

`z-index`는 **같은 stacking context 안에서만 비교됩니다.** 서로 다른 stacking context에 속한 요소들의 z-index는 직접 비교가 불가능합니다.

Stacking context는 다음과 같은 상황에서 새로 생성됩니다:

| 속성 | 조건 |
|------|------|
| `position` | `relative/absolute/fixed/sticky` + `z-index`가 `auto`가 아닐 때 |
| `opacity` | `1` 미만 |
| `transform` | `none`이 아닐 때 |
| `filter` | `none`이 아닐 때 |
| `isolation` | `isolate` |

툴팁에 `z-index: 9999`를 설정해도, 툴팁의 조상 중 하나가 낮은 z-index를 가진 stacking context 안에 있다면 다른 요소에 가려질 수 있습니다.

<Callout type="warning" title="z-index: 9999의 한계">
높은 z-index는 같은 stacking context 안에서만 효과가 있습니다.
모달 오버레이가 `z-index: 100`인 stacking context를 만들었다면, 그 안의 툴팁은 `z-index: 9999`여도 모달 외부의 `z-index: 200` 요소 뒤에 숨을 수 있습니다.
</Callout>

## 2. 세 문제를 한 번에 해결하는 방법: Portal

세 원인 모두 공통된 해결책이 있습니다. **툴팁을 DOM 트리에서 탈출시키는 것**입니다.

React의 `createPortal`은 컴포넌트를 원래 부모 트리가 아닌 다른 DOM 노드에 렌더합니다. 보통 `document.body`를 대상으로 씁니다.

<CodeTitle name="PortalTooltip.tsx">
```tsx
import { createPortal } from "react-dom";

function TooltipPortal({ children }: { children: React.ReactNode }) {
  return createPortal(children, document.body);
}
```
</CodeTitle>

`document.body` 직하에 마운트된 요소는:

- `overflow: hidden`인 조상이 없음 → 잘리지 않음
- `transform`을 가진 조상이 없음 → `position: fixed`가 진짜 viewport 기준으로 동작
- 독립적인 stacking context에서 렌더 → z-index 격리 문제 없음

<Callout type="tip" title="이벤트 버블링은 그대로">
Portal로 다른 DOM 위치에 렌더되어도, React의 이벤트 버블링은 **가상 DOM 트리(fiber 트리)** 를 따릅니다.
즉, Portal 내부의 클릭 이벤트는 원래 부모 컴포넌트까지 버블링됩니다. DOM 위치와 React 이벤트 경로는 별개입니다.
</Callout>

## 3. `getBoundingClientRect()`로 위치 계산하기

Portal로 렌더된 툴팁은 `document.body` 소속이기 때문에 트리거 요소의 위치를 직접 알 수 없습니다. 위치를 JS로 계산해서 주입해야 합니다.

`getBoundingClientRect()`는 DOM 요소의 **뷰포트 기준 좌표**를 반환하는 메서드입니다.

```
viewport
┌─────────────────────────────────────┐
│                 ↑ rect.top          │
│   ←rect.left→  ┌──────────────┐    │
│                │   element    │    │
│                └──────────────┘    │
│                 ↓ rect.bottom       │
└─────────────────────────────────────┘
```

반환되는 `DOMRect` 객체의 주요 프로퍼티:

| 프로퍼티 | 의미 |
|---------|------|
| `top` | 뷰포트 상단 ↔ 요소 상단 거리 |
| `left` | 뷰포트 좌측 ↔ 요소 좌측 거리 |
| `width` | 요소 너비 |
| `height` | 요소 높이 |
| `bottom` | `top + height` (= 뷰포트 상단 ↔ 요소 하단) |
| `right` | `left + width` |

`position: fixed`도 뷰포트 기준으로 배치되기 때문에, `getBoundingClientRect()`의 좌표를 `fixed` 요소의 `left`, `top`에 그대로 사용할 수 있습니다. 스크롤 오프셋을 더할 필요가 없습니다.

<Callout type="info" title="문서 절대 좌표가 필요하다면">
`position: absolute` 기반 배치처럼 페이지 전체 기준의 절대 좌표가 필요하다면 `scrollY`를 더해야 합니다.

```js
const absoluteTop = rect.top + window.scrollY;
const absoluteLeft = rect.left + window.scrollX;
```
</Callout>

### 트리거 중앙 위에 배치하는 공식

툴팁을 트리거 요소의 수평 중앙, 바로 위에 위치시키는 계산은 다음과 같습니다.

<CodeTitle name="useTooltip.ts">
```ts
function useTooltip() {
  const [pos, setPos] = useState({ x: 0, y: 0, visible: false });

  const show = (e: React.MouseEvent<HTMLElement>) => {
    const rect = e.currentTarget.getBoundingClientRect();

    setPos({
      x: rect.left + rect.width / 2,  // 요소의 수평 중앙
      y: rect.top,                    // 요소의 상단 (툴팁은 위에서 translate로 올림)
      visible: true,
    });
  };

  const hide = () => setPos(p => ({ ...p, visible: false }));

  return { pos, show, hide };
}
```
</CodeTitle>

좌표를 `fixed` 요소에 적용할 때는 `transform: translate(-50%, -100%)`로 수평 중앙 정렬과 요소 위 배치를 동시에 처리합니다.

```tsx
<div style={{
  position: "fixed",
  left: pos.x,
  top: pos.y,
  transform: "translate(-50%, -100%)",  // ← 수평 중앙 + 요소 위로 이동
  marginTop: -8,                        // ← 요소와의 간격
}} />
```

## 4. 뷰포트 경계 감지 (Flip Logic)

화면 상단에 있는 요소에 툴팁을 올리면 뷰포트 밖으로 잘려나갈 수 있습니다. 이를 방지하기 위해 **공간이 부족하면 반대 방향으로 flip**하는 로직을 추가합니다.

<Steps>
  <Step title="상단 공간 계산">
    `rect.top`이 툴팁 높이보다 작으면 위 공간이 부족합니다.
    툴팁 높이는 `tooltipRef.current?.offsetHeight`으로 미리 측정하거나, 고정값을 사용합니다.
  </Step>
  <Step title="방향 결정">
    ```ts
    const placement = rect.top > TOOLTIP_HEIGHT + GAP ? "top" : "bottom";
    ```
  </Step>
  <Step title="방향에 따라 좌표 분기">
    ```ts
    const y = placement === "top"
      ? rect.top            // 요소 위 → transform으로 올림
      : rect.bottom;        // 요소 아래 → transform 없이 그대로 내림
    ```
  </Step>
  <Step title="화살표 방향도 함께 전환">
    방향 정보를 상태로 관리하고, 툴팁 컴포넌트에서 화살표의 `border-color` 방향을 조건부로 변경합니다.
  </Step>
</Steps>

좌우 경계도 같은 방식으로 처리합니다.

```ts
// 좌측 경계 처리: 툴팁이 뷰포트 왼쪽을 벗어나면 오른쪽 정렬로 클램핑
const clampedX = Math.max(
  TOOLTIP_WIDTH / 2,                    // 좌측 최소값
  Math.min(x, window.innerWidth - TOOLTIP_WIDTH / 2)  // 우측 최대값
);
```

## 5. `ref` 없이 위치를 얻는 방법

Portal 기반 툴팁에서 트리거 요소의 위치를 얻기 위해 반드시 `ref`가 필요하지는 않습니다.

<Tabs items={["이벤트에서 직접 (ref 불필요)", "ref로 명시적 접근"]}>
  <Tab>
    `onMouseEnter` 이벤트가 발생한 순간, `e.currentTarget`이 이벤트를 받은 요소 자신입니다.
    그 시점에 `getBoundingClientRect()`를 호출하면 됩니다.

    ```tsx
    <button onMouseEnter={(e) => {
      const rect = e.currentTarget.getBoundingClientRect();
      // rect를 상태에 저장
    }}>
      hover me
    </button>
    ```

    이벤트 핸들러 안에서는 이 방식으로 충분합니다.
  </Tab>
  <Tab>
    이벤트 없이 위치가 필요한 경우 — 예를 들어 스크롤/리사이즈 시 툴팁 위치를 재계산하거나,
    외부에서 명령형으로 툴팁을 열 때는 `ref`가 필요합니다.

    ```tsx
    const triggerRef = useRef<HTMLButtonElement>(null);

    // 스크롤 이벤트에서 재계산
    useEffect(() => {
      function reposition() {
        if (!triggerRef.current) return;
        const rect = triggerRef.current.getBoundingClientRect();
        // 위치 업데이트
      }
      window.addEventListener("scroll", reposition, { passive: true });
      return () => window.removeEventListener("scroll", reposition);
    }, []);
    ```
  </Tab>
</Tabs>

## 6. 스타일 불변성 설계 원칙

Portal로 DOM 위치 문제를 해결했더라도, 툴팁의 **스타일이 부모에 오염되지 않도록** 설계해야 합니다.

<Tabs items={["CSS 오염 차단", "폰트·색상 초기화", "z-index 전략"]}>
  <Tab>
    CSS Cascade는 부모의 스타일이 자식에게 상속됩니다. `color`, `font-size`, `line-height`, `font-family` 등이 대표적입니다.

    Portal로 `document.body`에 마운트하면 대부분의 앱 스타일 컨텍스트를 탈출하지만, 글로벌 CSS가 `body` 자식에 적용되는 경우를 대비해 툴팁 루트에 명시적으로 초기화하는 것이 안전합니다.

    ```css
    .tooltip-root {
      all: initial;            /* 모든 inherited 속성 초기화 */
      font-family: system-ui;  /* 이후 명시적으로 재설정 */
      font-size: 13px;
    }
    ```

    `all: initial`은 너무 공격적일 수 있으므로, 필요한 속성만 명시적으로 재선언하는 방식이 더 실용적입니다.
  </Tab>
  <Tab>
    `em` 단위는 부모의 `font-size`를 기준으로 계산됩니다. 툴팁 내부에서 `em`을 쓰면 부모의 폰트 크기에 따라 크기가 달라집니다.
    툴팁처럼 스타일이 일정해야 하는 컴포넌트에서는 `px`이나 `rem`을 사용합니다.

    ```css
    .tooltip {
      font-size: 13px;         /* px — 부모 font-size 영향 없음 */
      line-height: 1.5;        /* unitless — 요소 자신의 font-size 기준 */
      color: #f1f5f9;          /* 명시적 색상 — 상속 차단 */
    }
    ```
  </Tab>
  <Tab>
    Portal로 `document.body`에 렌더된 툴팁에는 높은 `z-index`를 줍니다.
    앱의 레이어 체계를 미리 정의해 두는 것이 유지보수에 좋습니다.

    ```ts
    // z-index 레이어 상수
    const LAYERS = {
      base:    0,
      card:    10,
      dropdown: 100,
      modal:   200,
      toast:   300,
      tooltip: 400,  // 항상 최상위
    } as const;
    ```

    Portal 툴팁은 별도의 stacking context를 만들지 않으므로, 이 값이 실제로 다른 요소들과 비교됩니다.
  </Tab>
</Tabs>

## 7. 완성된 구조 정리

<Steps>
  <Step title="트리거에서 이벤트 감지">
    `onMouseEnter`에서 `e.currentTarget.getBoundingClientRect()`로 좌표를 읽고 상태에 저장합니다.
  </Step>
  <Step title="뷰포트 경계 계산 (Flip)">
    상단/하단/좌우 공간을 확인해 툴팁 배치 방향(`placement`)을 결정합니다.
  </Step>
  <Step title="Portal로 document.body에 렌더">
    `createPortal`로 DOM 트리를 탈출합니다. 어떤 조상의 `overflow`, `transform`, `z-index`에도 영향받지 않습니다.
  </Step>
  <Step title="position: fixed + 계산된 좌표 적용">
    저장한 좌표를 `fixed` 요소의 `left`, `top`에 주입합니다. `transform: translate(-50%, -100%)`로 중앙 정렬과 방향을 처리합니다.
  </Step>
  <Step title="스타일 명시적 선언으로 상속 오염 차단">
    폰트, 색상, 크기를 `px`/`rem` 단위로 명시 선언해 부모 스타일의 영향을 받지 않도록 합니다.
  </Step>
</Steps>

<ProsCons>
  <Pros title="Portal + getBoundingClientRect 방식의 장점">
    - `overflow: hidden`, `transform`, `z-index` stacking 문제를 모두 해결
    - 트리거 요소에 별도 CSS 규칙이 필요 없음 — 어떤 요소에든 붙일 수 있음
    - Flip 로직으로 뷰포트 경계 대응 가능
    - 스타일을 완전히 격리해 디자인 일관성 보장
  </Pros>
  <Cons title="고려할 점">
    - CSS-only 대비 JS 실행이 필요 — 스크롤 중 재계산이 필요하면 `scroll` 이벤트 리스너 추가
    - SSR 환경에서 `document.body`는 서버에 존재하지 않음 → 마운트 여부를 체크해야 함
    - 요소 크기가 동적으로 바뀌면 위치를 재계산해야 함 (`ResizeObserver` 활용)
  </Cons>
</ProsCons>

## 핵심 요약

<Callout type="success" title="정리">
- **`overflow: hidden`** 조상은 `position: absolute` 툴팁을 잘라냅니다. `position: fixed`로 탈출할 수 있지만...
- **`transform`/`filter`/`will-change`** 조상은 새로운 containing block을 만들어 `position: fixed`조차 가둡니다.
- **`createPortal`** 은 DOM 트리를 탈출해 `document.body`에 직접 마운트합니다. 어떤 조상 스타일에도 영향받지 않습니다.
- **`getBoundingClientRect()`** 는 뷰포트 기준 좌표를 반환합니다. `position: fixed`와 좌표 체계가 동일하므로 바로 사용할 수 있습니다.
- **`onMouseEnter`** 이벤트의 `e.currentTarget`에서 직접 좌표를 읽으면 `ref` 없이 위치 계산이 가능합니다.
- **스타일 불변성**을 위해 폰트/색상을 `px`/`rem`으로 명시 선언하고 상속을 차단합니다.
