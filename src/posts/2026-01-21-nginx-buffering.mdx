UI 서빙을 위한 웹 서버 하드웨어 스펙을 산정할 때, 흔히 하는 착각이 있습니다.

> "클라이언트 수가 늘지 않으면 부하도 늘지 않을 것이다."

이 판단의 근거는 보통 다음과 같습니다.
1. 브라우저 레벨에서 동시 연결 수를 제한하므로 네트워크 사용량이 크지 않을 것이다.
2. 네트워크 속도 한계로 인해 소수의 클라이언트가 대역폭을 독점할 수 없을 것이다.

하지만 이는 **'파일 업로드'**라는 변수를 만나면 완전히 빗나간 예상이 됩니다. 웹 서버의 부하는 단순한 데이터 양이 아니라, **연결 유지 시간과 리소스 점유** 관점에서 봐야 하기 때문입니다.

## 1. 파일 업로드가 위험한 이유: 스레드 고갈

결론부터 말하자면, 웹 서버를 경유하는 파일 업로드는 심각한 부하를 줄 수 있습니다. 업로드 작업 자체의 CPU 부하보다는, **느린 클라이언트를 기다리는 동안 서버의 메모리와 스레드가 묶이기 때문**입니다.

소수의 클라이언트라면 괜찮지만, 동시 접속자가 조금만 늘어도 **스레드 풀(Thread Pool) 고갈**로 이어져, 파일 업로드를 하지 않는 일반 사용자의 요청까지 처리하지 못하는 장애(Hang)가 발생합니다.

---

## 2. Nginx는 어떻게 백엔드를 보호하는가?

대부분의 아키텍처에서 앞단에 있는 Nginx는 **Request Buffering** 전략을 통해 뒷단의 비싼 백엔드(Java/Node.js)를 보호합니다.



<Steps>
  <Step title="1. 수신 (Client → Nginx)">
    브라우저가 파일 전송을 시작합니다. Nginx는 데이터를 받습니다.
  </Step>
  
  <Step title="2. 버퍼링 (Buffering & Disk Write)">
    * 들어오는 파일 크기가 메모리 버퍼보다 작으면 메모리에서 처리합니다.
    * **파일이 버퍼보다 크면:** Nginx는 이를 **디스크의 임시 디렉토리**에 씁니다. (Write I/O 발생)
  </Step>
  
  <Step title="3. 전달 (Nginx → Backend)">
    업로드가 완전히 완료되면, Nginx는 디스크에 쓴 파일을 다시 읽어서(Read I/O 발생) 뒤쪽 서버(Java)로 보냅니다.
  </Step>
</Steps>

이 과정에서 Nginx는 중계소 역할을 위해 하드디스크를 혹사시킵니다. 정작 가벼운 정적 파일 서빙이 디스크 I/O 병목으로 인해 느려질 수도 있습니다.

**그럼에도 불구하고 왜 이런 비효율적인 짓을 할까요?**

---

## 3. 시나리오 비교: 왜 버퍼링이 필요한가?

Nginx는 **"비싼 몸인 Java 스레드"**를 보호하기 위해 궂은일을 자처하는 것입니다.
**100MB 파일을 100초 동안 전송하는 느린 클라이언트** 상황을 가정해 봅시다.

<Tabs items={['상황 A: 버퍼링 없음 (Direct)', '상황 B: 버퍼링 있음 (Nginx Default)']}>
  <Tab>
    Nginx가 데이터를 받는 족족 Java로 토스한다고 가정해 봅시다.
    
    1. 브라우저가 1MB를 보냅니다.
    2. Nginx가 그 1MB를 바로 Java에게 줍니다.
    3. <Strong>Java는 100MB를 다 받을 때까지 100초 동안 스레드를 점유한 채 대기합니다.</Strong>
    
    **결과:** 이런 느린 사용자가 200명만 있어도 Java 스레드 200개가 100초 동안 마비됩니다. 서버는 다운됩니다.
  </Tab>
  <Tab>
    Nginx가 파일을 다 받을 때까지 Java와 연결하지 않고 대기합니다.
    
    1. Nginx가 100초간 브라우저와 씨름하며 데이터를 받아 디스크에 적어둡니다. (Java는 휴식 중)
    2. 전송이 끝나는 순간, Nginx는 Java에게 연결을 맺고 순식간에 파일을 밀어 넣습니다.
    
    **결과:** Java 스레드는 전송이 완료된 데이터를 처리하는 **0.08초** 동안만 점유됩니다. 200명이 와도 끄떡없습니다.
  </Tab>
</Tabs>

## 4. 속도의 차이: 내부망의 마법

이 전략이 유효한 이유는 Nginx와 백엔드 서버가 **같은 네트워크(VPC) 혹은 같은 서버** 안에 있다는 가정 덕분입니다.

<Callout type="info" title="네트워크 속도 비교">
  * **사용자 ↔ Nginx (외부망):** LTE/WiFi 환경. 매우 느리고 불안정함 (수십 Mbps)
  * **Nginx ↔ Java (내부망):** 데이터센터 내부 광케이블 혹은 Loopback. 매우 빠름 (수십 Gbps)
</Callout>

| 구분 | 대역폭 (속도) | 100MB 전송 시 소요 시간 | **Java 스레드 점유 시간** |
| :--- | :--- | :--- | :--- |
| **User → Nginx** | 10 Mbps | **80초** | (버퍼링 시) **0초** |
| **Nginx → Java** | 10 Gbps | **0.08초** | **0.08초** (순식간) |

이 덕분에 파일 업로드가 느린 원인이 브라우저의 파일 읽기 속도가 아니라, **Nginx가 열심히 버퍼링 중이었기 때문**이라는 것을 알 수 있습니다.

## 5. 결론: 트레이드오프

우리는 Java의 안녕을 위해 Nginx의 디스크를 희생시킨 것입니다.

<ProsCons>
  <Pros title="Nginx 버퍼링의 이점">
    * **Backend 보호:** 비싼 애플리케이션 서버의 스레드 고갈을 막아 줍니다.
    * **안정성:** 느린 클라이언트 공격(Slowloris 등)으로부터 백엔드를 격리합니다.
  </Pros>
  <Cons title="고려해야 할 비용">
    * **Disk I/O 폭증:** 동시 업로드가 많아지면 Nginx 서버의 디스크 대역폭이 포화 상태가 될 수 있습니다.
    * **응답 지연:** 디스크 I/O로 인해 정작 가벼운 정적 파일(JS, CSS) 서빙까지 느려질 수 있습니다.
    * **디스크 용량:** 임시 파일이 쌓일 충분한 디스크 공간이 필요합니다.
  </Cons>
</ProsCons>
